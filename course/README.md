# 📊 المقارنة بين بروتوكول Streamable HTTP وبروتوكول SSE (Server-Sent Events)

| الميزة | Streamable HTTP Transport | SSE Transport |
| :--- | :--- | :--- |
| **الآلية الأساسية** | طلبات HTTP معيارية (`POST` / `GET`) | تدفق مستمر وطويل الأجل عبر `EventSource` |
| **معرّف الجلسة (Session ID)** | ترويسات HTTP مخصصة (`mcp-session-id`) | معلمات الاستعلام في الرابط (`?sessionId=...`) |
| **دورة حياة الاتصال** | حسب الطلب (Stateless / On-demand) | اتصال دائم وطويل الأجل (Long-lived stream) |
| **تحليل جسم الطلب (Body Parsing)** | متوافق مع `express.json()` مباشرة | يتطلب التعامل مع التدفق الخام قبل التحليل |
| **التوافق مع Serverless** | **ممتاز** (Vercel, AWS Lambda, Cloudflare) | **ضعيف** (بسبب قيود مهلة الاتصالات المستمرة) |
| **تعقيد التنفيذ** | منخفض (ممارسات REST/HTTP القياسية) | متوسط (يتطلب إدارة حالة المقبس وإعادة الاتصال) |

---

## 🔍 التحليل التفصيلي

### 1. بروتوكول Streamable HTTP (`StreamableHTTPServerTransport`)

#### الآلية
بدلاً من إبقاء اتصال TCP مفتوحاً باستمرار، يتعامل هذا البروتوكول مع الاتصالات كمعاملات HTTP POST منفصلة. وتكون الاستجابات إما بيانات JSON قياسية أو تدفقات مجزأة (Chunked Streams) بناءً على ترويسات الطلب.

#### الإيجابيات
- **القابلية للتوسع**: يعمل بسلاسة داخل بيئات التوسع التلقائي والبيئات البيلاخادمية (Serverless).
- **التوافق مع البرمجيات الوسيطة (Middleware)**: يتكامل بدون تعارض مع برمجيات Express مثل `express.json()`، وبرمجيات المصادقة، وإعدادات CORS.
- **إدارة الجلسات عبر الترويسات**: تتبع أسهل وأكثر أماناً للسياق باستخدام ترويسات HTTP القياسية (`mcp-session-id`).

#### السلبيات
- مواصفة أحدث نسبياً مقارنة ببروتوكول SSE التقليدي.

---

### 2. بروتوكول SSE (`SSEServerTransport`)

#### الآلية
يبدأ بفتح تدفق HTTP GET أولي (`/mcp/sse`) حيث يبقي الخادم الاتصال مفتوحاً لإرسال الأحداث. بينما تُرسل رسائل العميل بشكل منفصل عبر مسار فرعي (`/mcp/messages?sessionId=...`).

#### الإيجابيات
- **دعم مدمج في المتصفح**: يدعم التدفق المباشر عبر API الـ `EventSource` دون مكتبات إضافية.
- **مثالي للخوادم الدائمة**: مناسب للتحديثات اللحظية الموجهة من الخادم على البنيات التحتية التقليدية (VPS / Docker).

#### السلبيات
- **غير مناسب للبيئات البيلاخادمية (Serverless)**: تقوم دالات Edge وLambdas بقطع الاتصالات الطويلة بسبب مهل التأخير (Timeouts).
- **استهلاك الموارد**: إبقاء الاتصالات الخاملة مفتوحة يستهلك ذاكرة الخادم ومقابض المقابس (Sockets).
- **تعارضات تحليل البيانات (Body Parsing)**: يتطلب ترتيباً دقيقاً للبرمجيات الوسيطة لتجنب استهلاك التدفقات الخام قبل معالجتها.

---

## 💡 التوصية والترجيح

- **اختر Streamable HTTP Transport** إذا كنت تنشر المشروع على **Vercel، AWS Lambda، Cloudflare Workers**، أو تبني خدمات مصغرة (Microservices) تعتمد على تدفق طلب/استجابة مباشر.
- **اختر SSE Transport** إذا كان مشروعك مستضافاً على **سيرفر خاص (VPS)، Railway، Render، أو حاوية Docker**، وتعتمد بشكل رئيسي على الإشعارات والتحديثات اللحظية المدفوعة من الخادم.
